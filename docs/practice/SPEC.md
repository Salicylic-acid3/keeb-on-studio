# Keeb-On! Studio タイピング練習 ＋ セットアップガイド 仕様メモ

作成: 2026-10-17（要件ヒアリングの結果をまとめたもの）
置き場所の想定: keeb-on-studio リポジトリ `docs/practice/SPEC.md`
作業ブランチの想定: `practice`

---

## 1. 目的と位置づけ

- 自作キーボードは用途に合わせたリマップが前提。その「どう決めればいいか」を段階的に導き、決めた配列をそのまま練習して身体に入れるまでを一本の流れにする。
- 既存のタイピングサイトとの違いは、**自分の実キーマップ（レイヤー含む）を画面に出したまま練習でき、誤打鍵が配列の見直しに直結する**こと。
- ZMK版・QMK版の両方で使う。見た目・操作感は既存の Keeb-On! Studio に合わせる（別ツールに見える独自UIは不可）。
- UIは日本語のみ。

## 2. 用語

| 用語         | 意味                                                                |
| ------------ | ------------------------------------------------------------------- |
| サイズクラス | 一般的なレイアウト換算での 30 / 40 / 60 / 75 / 80。ガイドの分岐単位 |
| ガイド       | キーマップ設計手順を順に導く対話式の流れ                            |
| 自由練習     | ガイドを通らず、今のキーマップで練習だけする使い方                  |
| ステップ     | ガイドの1単位（説明 → 問いかけ → 配置案 → 適用/スキップ）           |
| 課題         | 文章では練習できない操作（カーソル移動・テンキーなど）の練習単位    |
| 入力不可文字 | 現在のキーマップのどのレイヤーにも割り当てが無く、入力できない文字  |

## 3. 入口と画面構成

- URL: `keeb-on.studio/practice` の1ページ。ページ内のモードとして「セットアップガイド」「自由練習」を持つ。
- 入口: ZMK版・QMK版それぞれの**キー設定（リマップ）画面にボタン**を置く。トップ画面からの導線は必須ではない。
- デモモード（実機未接続）でもガイドの説明・配置案・適用までは動く。実機が必要な部分（親指スペース計測、実打鍵の練習）は未接続時に「自分で選ぶ」「接続してから練習」に切り替える。
- 実機接続時は実機から読んだ現在のキーマップを使う。未接続時は登録機種のデフォルトキーマップ（keyboard-test と同じソース）を使う。
- ZMKの無線（BLE）接続中も、既存のリマッパーが読める範囲でキーマップを読む。

## 4. 前提条件と注意書き

- ブラウザのキーイベント（`keydown` の `event.key`）で判定する。**IMEはオフ**にしてもらう（練習開始時に案内を出す）。
- OSのキーボード配列（US / JIS）は、**リマッパーで選択済みの値を初期値**にし、練習開始時に明示的に変更もできるようにする。
- タイピング練習中はページがキーボードフォーカスを持つ必要があるため、練習エリアをクリックして開始する形にする。ブラウザのショートカットと衝突するキー（Tab, Ctrl+W 等）は `preventDefault` で抑止する。
- スマホ・タブレットは対象外（物理キーボードが前提）。レイアウトエディタのようなタッチ対応は不要。

## 5. セットアップガイド

### 5.1 分岐

- 機種メタデータ（§8）の `sizeClass` と `defaultGuide` で分岐を決める。
- **30%・40%以下・60%以上**の3系統のガイドを用意する。75 / 80 は 60 系統に含め、差分（Fキー列・ナビキーの有無）は文章の差し替えで吸収する。
- 「30%に挑戦」ボタン: 40%以下の機種で、アルファベットの単押し/長押し設定（Home Row Mods・アルファベット長押しレイヤー）まで踏み込みたい人向けに、30%系統のガイドへ切り替えられる。
- BeThirty系はもともと30%なので、30%系統がデフォルト。

### 5.2 ステップ構成

#### 40%以下（基本形）

1. **導入**: デフォルトレイヤーの考え方。よく使うキーから優先的に置く、という方針の説明。
2. **記号の優先順位**: ハイフン・コロン・セミコロン・クォート・スラッシュ・バックスラッシュ等のうち、よく使う順を選んでもらう（並べ替えまたは上位N個の選択）。回答からベース層の記号位置の配置案を生成。例文: 「私はコロンよりハイフンをよく使うので、コロンの位置にハイフンを置いている」。
3. **重複キーの整理**: CapsLock など使用頻度の低いキーを Ctrl 等に置き換える提案。機種ごとに Esc / Tab / CapsLock のデフォルト位置は決まっているので選ばせず、「置き換えるか・残すか」だけ問う。
4. **親指キー**: 親指スペース計測（§5.4）でスペースの位置を決め、残りの親指キーに Backspace / Delete / Enter をよく使う順で割り当てる案を出す。
5. **レイヤーキー**: 単押し/長押しの分離の説明（スペースやEnterの長押しは通常使わないので長押しをレイヤーにできる、Backspace/Deleteは長押しで連続削除するのでレイヤーには向かない）。どの親指キーをレイヤーキーにするかを提案。
6. **【練習】ベースレイヤー**: ベース層だけで打てる文章で練習。
7. **レイヤーの中身（片手で完結させたいもの）**: 「右手だけで動かしたいもの（カーソル）」「左手だけで打ちたいもの（記号）」をレイヤーキーを押す手との関係で提案。記号はモディファイア無しで出るようにする（3キー同時押しを避ける）。
8. **レイヤーの中身（反対側）**: テンキー・ファンクションキーをどちらの手に置くか。
9. **【練習】レイヤー課題**: カーソル移動・テンキー・Fキーを課題形式で練習。
10. **たまに使うキー**: PrintScreen 等を別のレイヤーキーの奥に入れる。
11. **【練習】総合**: ベース＋レイヤーを混ぜた文章・課題。→ 結果画面（§7）。

#### 60%以上

1. 導入。
2. **踏襲か、少し変えるか**: 今まで使っていたキーボードの配列をそのまま使うか、少し変える気があるかを問う。
   - 踏襲 → 【練習】ベース → レイヤーキー（Fnキーがある機種のみ）→ 中身 → 【練習】→ 結果。
   - 少し変える → 記号の例（ハイフン/コロン）、CapsLock の置き換えを提案 → 以降は 40% と同じ流れ（親指キーの自由度は低いので、親指計測は親指キーが複数ある機種のみ）。

#### 30%

1. 導入（30%特有の前提: アルファベットキー自体に長押しの役割を持たせる）。
2. **親指とアルファベット長押しの役割分担**: Home Row Mods（ホームロウ長押しでモディファイア）と、アルファベット長押しでレイヤーの両方を扱う。どの指にどのモディファイアかの定番と、タップ/ホールド判定時間に関する注意（誤発動の説明はユーザー目線で、内部処理は書かない）。
3. 記号の優先順位（40%と同じ、ただし置ける数が少ないので上位数個）。
4. 以降は 40% の 4〜11 に準じる。

### 5.3 ステップの画面構成

- 左: 説明文と問いかけ（選択肢・並べ替え）。右（または下）: 現在のキーマップ描画。
- 配置案を生成したら、**設定すべきキーをハイライト**し、「適用する」「設定せずに次へ」の2ボタンを置く。適用は既存のリマッパーの保存経路を使う（デモモードではローカルの編集状態に反映）。
- 「適用」後に個別に直したい場合はリマッパー画面へ飛べるリンクを置く（戻ってきたら同じステップから再開）。
- ステップの一覧（進捗バー）を常時表示し、任意のステップへ戻れる。

### 5.4 親指スペース計測

- 実機接続時のみ。親指キーをすべて一時的にスペース扱いにし（実機には書き込まず、ブラウザ側で「どの物理キーが押されたか」を判定できる仕組みが必要 → §13）、短い文章を打ってもらう。
- 親指キーごとの押下回数を集計し、最多の位置を「ここをスペースに」と提案する。
- 「自分で選ぶ」ボタンで計測を飛ばして手動選択もできる。

### 5.5 配置案の自動生成

- ルールベースで行う（機械学習等は不要）。
  - 記号: 優先順位の回答 → ベース層の「記号を置けるスロット」（機種メタデータの `symbolSlots`、無ければデフォルトキーマップで記号が入っている位置）に上から順に詰める。
  - 親指: 計測結果（または手動選択）→ スペース。残りの親指スロットに Backspace / Delete / Enter を回答順に。
  - レイヤーキー: 長押しレイヤーを持たせる親指スロットを提案（スペース・Enter優先、Backspace/Delete は避ける）。単押しは元のキーを維持（LT / &lt 相当）。
  - レイヤーの中身: 「右手カーソル・左手記号」「右手テンキー・左手Fキー」のテンプレートを、レイヤーキーを押す手に応じて左右反転して当てる。
- 生成結果はあくまで案。ユーザーが選択肢で左右やキーを入れ替えられるようにする。

### 5.6 練習の挿入位置

- **レイヤーが1つ完成するごと**に練習を挟む（ベース完成 → 練習、各レイヤー完成 → 課題）。ステップごとの小練習は入れない。

### 5.7 進捗の保存と再開

- ステップの進捗・回答内容・適用済みフラグをブラウザのローカル保存（localStorage）に機種IDごとに持つ。
- 次回 `/practice` を開いたとき「前回の続きから」を出す。

## 6. タイピング練習

### 6.1 判定方式

- 期待文字列と、ブラウザが受け取った文字を1文字ずつ照合する。**どのキーを押したかではなく、出力された文字だけで判定**する。
- タップダンス・コンボ・マクロ・モディファイア組み合わせは結果の文字だけ見る。判定できないキーが押されても、正しい文字が出れば次へ進む。
- 日本語の練習テキストはローマ字で打つ。**表記揺れはすべて正解**とする（し=si/shi、ち=ti/chi、つ=tu/tsu、ふ=fu/hu、ん=n/nn/xn、ちゃ=tya/cha/cya、っ=子音重ね/xtu/ltu、ぢ=di/zi など）。かな→許容ローマ字集合の変換テーブルを持ち、文節ごとに受理可能な入力列を展開して照合する。
- 英数字・記号は1対1で照合する。

### 6.2 止まるモード / 進むモード

- 初期値は**止まるモード**。画面上のトグルで**進むモード**に切り替え可能（設定はローカル保存）。
- 止まるモード: 誤打鍵時はその文字で止まり、**現在のキーマップをレイヤー込みで逆引きして該当キーを光らせる**（レイヤー奥のキーなら、レイヤーキーも同時に光らせる）。
- 進むモード: 誤打鍵をカウントして次の文字へ進む。
- **入力不可文字**: 期待文字がどのレイヤーにも無い場合、その文字で止めず「このキーは設定されていないので入力できません」と表示して次へ進む。どちらのモードでも同じ挙動。結果画面で入力不可文字として一覧化する。

### 6.3 課題形式

- 文章で練習できない操作は課題にする。例:
  - カーソル: 「この行の3文字右へ移動」「上の行の行頭へ」（練習エリア内の仮想カーソルで判定）。
  - テンキー: 「123+456 を入力」「電話番号風の数字列」。
  - Fキー: 「F5 を押す」「F2 → 文字列入力 → Enter」。
  - ショートカット: 「Ctrl+C → Ctrl+V 相当を押す」（OSに合わせて Cmd と表示）。
- 課題でも入力不可（そのキーが無い）は同じ扱いで記録して進む。

### 6.4 練習テキスト

- 権利上問題のないものだけを使う。本人のブログ（salicylic-acid3.hatenablog.com）の記事から、40〜80文字程度の文を**こちらで自動抽出**して候補を作る。固有名詞・URL・コード片・引用部分は除外する。
- 抽出した文は `data/practice/texts.ja.json` のような形で、かな表記（ローマ字展開用）と表示用の漢字かな交じりの両方を持たせる。
- ベース層だけで打てる文／記号を含む文／数字を含む文、のタグを付け、ステップに応じて選ぶ。

## 7. 結果画面と出力

- 表示項目（初期版）:
  - 正確率、速度（文字/分、課題は所要時間）
  - キーマップ上に重ねた**誤打鍵ヒートマップ**（レイヤーごとに切替）
  - ミスの多いキー上位（期待キー／実際に押された文字のペア）
  - **入力不可文字の一覧**（文字とカウント）
- 出力: 結果を**画像（PNG）とPDF**で保存しやすくする。ボタン1つでダウンロード。レイアウトエディタのSNS画像化と描画基盤を共有する。
- 改善提案（「このキーのミスが多いので位置を見直しては」）は**ロードマップの後続フェーズ**（§12）。

## 8. 機種メタデータ

- 配置案の自動生成に必要な情報を、機種定義に小さなJSONを1つ足す形で持つ。
- **新機種を登録するときに対話形式で決めて保存**する（登録手順の一部として、質問に答えるとJSONが生成されるスクリプトまたはUI）。既存機種と同じ程度の労力で追加できること。
- 既存機種分は実装側で初期値を起こし、本人が確認する。

```jsonc
{
  "id": "goforty_max",
  "sizeClass": "40", // "30" | "40" | "60" | "75" | "80"
  "defaultGuide": "40", // BeThirty系は "30"
  "allowGuide": ["30", "40"], // 「30%に挑戦」を出すかどうか
  "split": true,
  "thumbKeys": [
    // 親指で押せるキー（物理位置インデックス＋手）
    { "pos": 36, "hand": "L" },
    { "pos": 37, "hand": "L" },
    { "pos": 38, "hand": "R" },
    { "pos": 39, "hand": "R" },
  ],
  "homeRow": { "L": [13, 14, 15, 16], "R": [19, 20, 21, 22] }, // 30%用
  "fixedKeys": { "esc": 0, "tab": 12, "capslock": null }, // 機種デフォルトの位置（nullは無し）
  "symbolSlots": [10, 11, 23, 35], // ベース層で記号を置けるスロット（省略時はデフォルトキーマップから推定）
  "defaultLayerKeys": [{ "pos": 37, "layer": 1, "hand": "L" }],
}
```

## 9. ガイド文章の構造

- 文章は**サイズクラス共通の本文＋機種ごとの差分**の二層。差分は「Enterの位置」「親指キーの本数」「Fキー列の有無」程度の変数で埋め込む（テンプレート変数）。
- 草稿はこちらで書き、本人が直す。説明文は内部処理に触れず「何が変わるか・どう決めるか」だけを書く（既存の設定項目の説明文と同じ方針）。
- 本人のキーマップ設計の考え方（記号の優先順位、親指キー、レイヤーキーの単押し/長押し分離、片手で完結させる配置、反対側にテンキー/Fキー、たまに使うキーは別レイヤー）を、そのまま各ステップの文章の骨にする。

## 10. 統計と保存

- 保存先は**ブラウザのローカル保存のみ**（クラウド同期なし）。
- 保存するもの: ガイド進捗（§5.7）、モード設定、直近の練習結果（結果画面の再表示用、件数上限あり）。
- 結果の持ち出しは画像/PDF（§7）で行う。

## 11. 初期版でやらないこと

- クラウドへの統計保存・機種をまたいだ集計
- 英語UI
- 改善提案（後続フェーズ）
- ロータリーエンコーダなど、Keeb-On! で対応しない機能の練習
- スマホ・タブレット対応
- タイピングサイト的なランキング・対戦

## 13. 未決事項・技術確認が必要なこと

1. **親指スペース計測の実現方法**: ブラウザは「どの物理キーが押されたか」を直接知れない。候補は (a) 計測中だけ親指キーに識別用の別キーコード（F13〜F24 等）を一時的に書き込んでブラウザで判別し終了後に戻す、(b) ZMK Studio / Vial の raw HID 経由で押下中の物理位置を読む。実装難易度と実機への書き込み回数を踏まえて決める。
2. **「設定されていない文字」の判定精度**: モディファイア付き（Shift+数字の記号など）やOS配列（US/JIS）差を考慮したうえで「どのレイヤーにも無い」と言い切る逆引きの作り方。
3. **適用経路**: ガイドからの「適用」が ZMK版・QMK版それぞれの既存保存処理をそのまま呼べるか（デモモードでの編集状態の扱いを含む）。
4. **課題の判定UI**: カーソル移動課題を練習エリア内の仮想エディタで判定する場合の見せ方。
5. **BeThirty系以外で30%系統をデフォルトにする機種があるか**（本人が機種一覧を精査する際に決める）。
